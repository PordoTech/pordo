# 视频更新功能方案

状态：桌面端已实现；更新列表和已看状态接入现有云同步。

视频页新增「更新」标签，按收藏的 UP 主展示新投稿。沿用漫画更新的首次建基线、后台检查、未看提醒和失败退避机制，复用视频封面卡片与现有播放流程。

## 页面结构

标签顺序为「收藏 / 搜索 / 更新」，与漫画页将更新放在搜索后的顺序一致。更新标签显示有未看投稿的 UP 主数量，例如「更新 · 3」；悬停提示「3 位 UP 主有 8 个未看视频」。没有更新时只显示「更新」。

标签行右侧放置现有样式的刷新图标。检查时原位旋转，提示「检查更新中 6/12」，保持图标尺寸和页面布局稳定。刷新不会清空当前列表。

```text
视频
收藏    搜索    更新 · 3                              ↻

⌄ [头像] UP 主 A       3 个未看        [全部标为已看] [查看投稿]
  [视频封面 16:9]  [视频封面 16:9]  [视频封面 16:9]
  视频标题         视频标题         视频标题
  今天 12:30       昨天 18:00        11 月 12 日

⌄ [头像] UP 主 B       5 个未看        [全部标为已看] [查看投稿]
  [视频封面 16:9]  [视频封面 16:9]  [视频封面 16:9]
  …
                          [展开其余 2 个]
```

每组默认展开，支持折叠并在本次会话内记住。分组按最新未看投稿时间倒序，同时间按收藏时间和 UID 稳定排序；组内按发布时间倒序，不用昵称或粉丝数参与更新身份判断。

每组先展示最多六个视频，「展开其余 N 个」在当前分组继续展示，避免离开更新页才能处理积压。页面按实际未看视频数计算计数，折叠或截断不改变数字。

点击头像或「查看投稿」进入现有 UP 主投稿浏览；从更新打开投稿或播放器后，返回应恢复更新标签、分组展开状态与滚动位置。

## 视觉与布局

直接使用 `src/app/design.rs` 的深色背景、薄荷绿强调色、正文和弱化文字、边线与按钮，不引入独立主题。

- 视频卡片复用 `online_video/cards.rs` 的 16:9 封面、标题、时长与发布时间布局；同组内省略重复的 UP 主名称。
- 沿用视频卡片的 12 间距和现有自适应列数，封面图按可视区域懒加载；不将漫画的竖版封面直接套到视频上。
- 分组标题使用 32 大小的头像、UP 主名称和弱化计数，主要信息保持紧凑；卡片未看标记使用薄荷绿小圆点或短标签。
- 展开队列或缩小窗口后减少列数，最窄一列；分组次要操作合并到「更多」菜单，不挤压昵称和未看计数。
- 刷新进度留在刷新按钮提示里，列表内容不因检查开始、结束或单个 UP 主失败而上下跳动。

## 订阅范围与首次基线

只检查应用内收藏的 UP 主。收藏单个视频不会自动订阅它的 UP 主，B 站账号的关注列表也不自动导入。

首次检查成功时，用当前最新投稿建立基线，不把历史视频全部标成新更新。已有收藏 UP 主升级后也按同一规则处理。首次检查失败显示「尚未完成首次检查」，成功前不伪造空基线。

基线必须保存已知 BV 号和发布时间边界。后续浏览投稿列表、补载历史视频时，早于初始基线的旧投稿只补充元数据，不能因第一次见到 BV 号就标成新投稿。

取消收藏后立即从更新视图和待检查队列移除，在途结果返回时再次检查收藏状态。首版重新收藏按新订阅重新建立基线，旧请求不能写回新订阅；为每轮订阅保留代次标识。

## 检查更新规则

沿用漫画更新的事件触发方式：启动、进入首页或视频更新页时检查是否到期，不增加持续后台定时轮询。建议正常自动检查间隔为 15 分钟，失败的 UP 主退避一小时；手动刷新允许立即重试。

收藏 UP 主后安排首次基线检查；自动检查使用「设置 → 视频 → 自动检查收藏 UP 主更新」，默认开启。关闭后仍可手动刷新。

复用当前 `Bilibili::uploads(mid, page)` 获取按发布时间排序的投稿。当前接口每页 20 条；检查只拉取列表元数据，用户点击视频后才请求详情与播放地址。

后续检查从第一页开始，按 BV 号去重并扫描整页，再依据已知投稿与发布时间边界判断是否需要继续翻页。不能以首页第一条或单个已知投稿作为停止条件，避免置顶、重排和同时间投稿影响结果。标题、封面或播放量变化只更新资料，不新增提醒。

长时间离线或高频投稿时继续翻页追到旧边界。建议单轮每个 UP 主最多检查五页，超过后显示「仍有投稿待补查」，保留继续检查进度；只有补查完整成功后才推进已完成的检查边界，避免跳过中间投稿。

建议最多同时检查两个 UP 主，同一 UP 主串行翻页，请求启动至少间隔两秒，单请求超时 20 秒。这些是首版调度参数，实施时通过模拟接口验证。重复点击刷新合并到当前轮次；重试沿用已有请求身份。

接口要求重新验证或出现明确限流时，停止本轮后续请求并显示对应入口或提示，不连续重试。单个 UP 主的普通请求失败只影响该组，其余 UP 主继续。

更新任务应独立于搜索和投稿浏览的请求状态。切换标签、打开投稿页或播放视频时，现有 `cancel_discovery()` 仍负责取消浏览请求，不取消或清空后台更新数据。

## 未看更新与播放

新发现的投稿进入所属 UP 主的未看集合；打开更新页、展开分组或进入 UP 主投稿页均不自动消除提醒。

点击卡片沿用现有视频播放流程。只有该视频成功开始播放后才自动标为已看，解析失败、加载失败和取消打开时保留未看状态。通过搜索、收藏或历史开始播放同一 BV 号时，也应更新这一标记。

单个视频菜单提供「标为已看」。分组提供「全部标为已看」，处理点击时已显示在该组中的未看集合，包含折叠的本地缓存项；随后到达的新投稿保持未看。批量操作提供短时撤销，撤销只恢复本次处理且仍受订阅状态约束的项，不回滚用户随后成功播放的变化。

这里的已看标记用于处理更新提醒，播放进度继续独立保存。开始观看一条新视频后，其他未看视频仍保留；整组处理完后移出更新列表，收藏 UP 主保留在收藏页。

首版按 BV 号识别一次投稿，一个视频的多个分 P 合并为一条。已有 BV 号追加分 P 不属于本轮「新投稿」检查范围。

## 异常与空状态

| 状态 | 展示与操作 |
| --- | --- |
| 没有收藏 UP 主 | 「收藏 UP 主，及时查看新投稿」，提供「搜索 UP 主」入口 |
| 尚未完成首次检查 | 「正在建立投稿基线」或对应失败提示，已有其他分组仍可浏览 |
| 检查完成且没有更新 | 「暂无新投稿」，显示最近成功检查时间 |
| 单个 UP 主检查失败 | 在该组标题显示弱化错误与「重试」；保留已有未看视频 |
| 失败但没有未看视频 | 在正常更新组之后显示紧凑的失败条目；错误不计入更新数量 |
| 离线 | 展示本地已缓存的列表元数据；点击播放仍按现有网络错误处理 |
| 视频无法播放 | 保留未看状态，展示原因，允许手动标为已看；一次缺席列表不推断视频已删除 |
| 数据保存失败 | 展示保存失败提示，不报告检查完成或批量标记成功，保留可重试状态 |

## 数据与模块边界

UP 主收藏继续由现有 `CreatorRecord` 管理。更新内容使用现有云同步日志持久化，不创建独立的本机更新库。订阅按来源、UID 与收藏时间区分，视频用来源与 BV 号作为稳定身份。

每个订阅同步初始边界、已完成检查边界、投稿摘要和单条已看标记，实际播放另有独立标记，使撤销手动处理不会恢复已播放的提醒。摘要保存 BV 号、标题、封面地址、时长、发布时间和所属 UID，不保存播放地址或账号凭据。检查与成功时间、失败退避、请求队列和分页补查游标只在当前会话中保留；重启后从第一页重新检查并用同步边界去重。

历史播放记录不作为唯一的已看依据，避免删除播放历史后旧更新重新出现。显式处理结果和已知身份应保留必要的去重信息；压缩已处理视频的展示缓存时不能清除未看投稿，也不能导致旧视频再次进入未看集合。

`online_video/updates.rs` 管理检查队列、合并与同步数据，`online_video/updates_ui.rs` 负责分组视图。更新页使用现有视频卡片，维持 UP 主投稿浏览、搜索和更新页的交互一致。

更新列表、检查边界和已看标记随现有云同步上传、合并和恢复。每条投稿与已看标记独立合并，使一台设备的新投稿不会覆盖另一台设备的已看状态。新设备等待首次云同步恢复基线后再建立尚无基线的订阅，避免把已同步的未看投稿当作首次基线消除。取消收藏和重新收藏使用独立订阅代次，旧请求不能写回新订阅。

未启用云同步时，更新列表和已看状态仅在本次会话中保留，启用后使用现有同步日志的离线待提交和关机检查点机制，不另建仅本机保存的更新列表文件。

## 验收重点

- 新增收藏与旧收藏首次检查不会导入大量历史更新；失败后重试可以建立基线。
- 多个 UP 主独立分组，昵称改变不影响身份；未看计数、排序和展开后数量一致。
- 跨页、离线积压、重复返回、置顶与同时间投稿不会漏掉已拉取的新视频或重复提醒；补查未完成时保留明确状态。
- 播放成功后标为已看，播放失败保留提醒；其他入口播放同一视频也能消除对应提醒。
- 单项处理、分组全部处理和撤销不回滚其后的新投稿或播放操作。
- 取消收藏、快速重新收藏、切换标签和打开播放器均不会让旧请求污染当前状态。
- 部分失败、限流、离线、存储失败和重启恢复行为可验证。
- 检查中刷新图标不变宽；窄窗口、右侧队列展开、中英文长标题下均保持可用。
- 两台设备并发检查和标为已看能够合并，实际播放标记不被另一台设备的手动撤销覆盖；同步期间产生的新投稿保留。
